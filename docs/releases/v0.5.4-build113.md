# iPac 0.5.4 / Build 113

日期：2026-11-26（台北）。針對來賓 macOS 開啟 App 緩慢，以及指標移動、捲動卡頓。以下量測分開列出 Build 112 的 iPad 觀察，以及 Build 113 的 Mac 受控測試；新版在 iPad 上的互動效果尚未驗收。

## 為什麼改

Build 112 在 iPad 上以 **8 核、1920 × 1336** 運行時，系統回報的熱狀態從正常、微溫升到嚴重（`serious`）。第二次以 **6 核、1600 × 1112** 運行時，各次取樣都已是嚴重。兩次 VM 都配置 6144 MiB RAM。核心數、解析度和熱狀態不同，不能用這兩次判定減核是否有效。日誌沒有硬體時脈或實際顯示 FPS，不能確認降頻幅度或卡頓的唯一原因。

## 改動與驗證

| 路徑 | 改了什麼 | 在 Mac 上驗到什麼 |
| --- | --- | --- |
| CPU 排程與高熱等待 | 預設恢復 Build 103 的「使用者啟動」優先權，不再讓所有虛擬 CPU 與輸入、畫面更新競用最高互動優先權。仍可手動選高優先權。高熱（嚴重或危急）時，虛擬核心短暫等待後會睡眠，直到另一核心回覆記憶體對映失效通知或重新檢查。 | 測試刻意延遲 240 次通知回覆；等待執行緒消耗的 CPU 時間從約 180 ms 降到約 4.5 ms，且收到所有回覆。這不是 240 次操作的耗時，也不是實機溫度。 |
| 滑鼠與觸控板 | 同一筆滑鼠位移的 X、Y 和同步事件一起通知 VM，不省略事件；減少觸控板重複喚醒及預設除錯輸出。 | 一筆雙軸滑鼠移動從喚醒 3 次減為 1 次，事件內容、順序不變；雙指測試的 7 筆 USB 報告全部送達。 |
| 開 App 時的磁碟讀取 | 同一筆磁碟讀取若有多段客體緩衝區，會合併讀入。保留寫入與同步政策；短讀只標記真正被覆寫的客體程式頁。 | 8 MiB 暖快取檔案，9 輪配對測試。每筆 4 段 × 16 KiB 從 7.88 降到 5.07 微秒，8 段從 15.96 降到 8.58 微秒。這不是 App 開啟時間。 |
| Metal 資源檢查 | 重用 GPU 緩衝區前直接比對頁面映射，不再先建一份臨時副本；映射改變時仍會重新處理。 | 同一個 1,253 頁資源，每次檢查約從 310 降至 120 奈秒。這是單次檢查，不是每幀耗時或 GPU FPS。 |

## 實機比較

1. 升級前在來賓 macOS 儲存工作、正常關機。不要刪除舊 App 或用跨版本快照取代正常關機。
2. 新版不會替既有 VM 改寫 RAM、核心數或解析度。比較前後版本時，固定這些設定，在相近的 iPad 熱狀態測試。
3. 用同一個 Finder 視窗拖曳、捲動，再開啟同一款 App，比較指標是否跟手、App 多久後可接受操作。第一次開啟和再次開啟分開比較；不要以背景畫面更新數代替互動 FPS。
